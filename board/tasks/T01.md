Audit every way a human or a machine can become an authenticated principal on this platform, and everything that keeps them authenticated. OTP issuance and verification, password login, JWT access + refresh rotation, session storage in KV, device binding, bot defence. This is the front door — a hole here makes every other track irrelevant.

## Questions you must answer

1. Trace OTP end to end: generation entropy, storage, TTL, attempt counter, lockout, reuse, and whether a verified OTP can be replayed. What happens when WhatsApp and Resend keys are both absent — can `devCode` ever reach a production response?
2. Can OTP verification create or elevate an account role? PR #20 claimed to fix admin-creation via OTP — verify the fix is still present and complete on current main.
3. JWT: signing algorithm, secret source, `alg` confusion, issuer/audience checks, clock skew, and whether expiry is actually enforced on every route or only some.
4. Refresh rotation: is the old refresh token invalidated atomically? What happens on concurrent refresh from two devices? Is there replay detection / reuse-detection family revocation?
5. Logout: does it revoke server-side, or only drop the client token? Same question for password change and for admin-initiated ban.
6. Password hashing: algorithm, cost factor, salt, and whether the password path bypasses any OTP-era rate limits.
7. Session storage in the `SESSIONS` KV namespace: what is stored, TTL, eventual-consistency implications of KV for revocation (KV reads can be stale for up to 60s — does that let a revoked token live on?).
8. Turnstile: is it enforced server-side or decorative? What happens when `TURNSTILE_SECRET_KEY` is absent — fail-open or fail-closed?
9. Device binding: does `routes/devices.ts` tie a session to a device? Can a stolen refresh token be used from a new device undetected?
10. Flutter token storage: secure storage vs shared preferences, token in logs, token in URLs, and behaviour on app backgrounding.
11. Admin auth: is the admin console using the same token surface as riders? Any privilege boundary at the token level?

## Benchmark against

- Uber/Careem: silent SMS + device attestation, step-up auth on sensitive actions, refresh-token reuse detection with family revocation.
- inDrive: phone-first onboarding with progressive profiling; account recovery flow that survives SIM change.
- Egyptian market reality: WhatsApp OTP as primary, SMS as fallback, low-end Android devices, users switching SIMs frequently.

## Shared context (identical for every task)

The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.
