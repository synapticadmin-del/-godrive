## Mission

Rider and captain are two halves of one transaction, built as two separate Flutter apps by different hands at different times. They have drifted. Put them side by side, screen by screen and state by state, and find every place where the two sides of the same trip disagree — visually, behaviourally, or factually. Then define the parity contract that keeps them aligned from now on.

## Questions you must answer

1. **The paired-state table — the core artefact.** For every trip state, produce a row: what the rider sees, what the captain sees, what the server holds, and whether the three agree. Cover at minimum: searching, offers arriving, offer accepted, captain en route, captain arrived, waiting, trip started, in transit, destination changed, trip completed, payment settled, cancelled by rider, cancelled by captain, no captain found, network lost mid-trip. Any row where the two apps tell different stories about the same moment is a finding.
2. **Duplicated code.** `trip_chat_screen.dart` and `trip_ws.dart` exist in both apps. Diff them. How much is identical, how much has diverged, and which divergences are bugs rather than intent? Same question for wallet, SOS, splash and login. Produce a concrete extraction plan into `packages/flutter_shared`.
3. **The chat is one conversation seen twice.** Compare both implementations: message ordering, read receipts, timestamps, retry on send failure, and what happens when one side is offline. Do both sides render the same history?
4. **Wallet vs earnings.** The rider sees a balance; the captain sees earnings. Same underlying ledger, two vocabularies. Are the numbers reconcilable? PR #52 explicitly matched the captain's balance card to the rider's — verify it held, and check whether the semantics (pending vs available vs settled) are consistent.
5. **SOS parity.** Two separate SOS screens. Do they trigger the same server behaviour, show the same confirmation, and offer the same actions? A safety feature that behaves differently for the two people in one car is a defect.
6. **Shared package discipline.** Inventory what lives in `flutter_shared` versus what has been copy-pasted. Which of the 15 shared widgets are used by both apps, which by one, and which are used by neither (dead code)?
7. **Dependency drift.** Diff the two `pubspec.yaml` files. Different versions of the same package across two apps in one monorepo is a maintenance trap — list every mismatch.
8. **Theme and token adoption.** Do both apps consume `flutter_shared/theme/app_theme.dart` identically, or has one drifted to local styling? Compare the same component (button, card, chip) rendered in each app and describe the visual delta.
9. **Terminology.** Build the glossary: does the rider say 'كابتن' where the captain app says 'سائق'? Is a 'trip' a 'ride' a 'رحلة' a 'مشوار' depending on which app you open? Do both use the same word for the same money concept? Inconsistent vocabulary across the two sides of one marketplace erodes trust — produce the canonical glossary and the list of violations.
10. **Notification symmetry.** For each trip event, does the counterpart get told? Rider cancels — is the captain notified with the same urgency and wording register? Build the matrix of event × rider notification × captain notification and find the holes.
11. **Timing symmetry.** When a state changes, do both apps learn about it at the same time, or does one poll while the other holds a socket? PR #53 added polling as a rider-side backstop — does the captain have an equivalent? Divergent latency creates the 'he says he arrived, my app says he's still coming' argument.
12. **Version and API contract.** Can rider v1.2 and captain v1.0 coexist on the same trip? Is there anything that forces both sides to a compatible version? (Coordinate with T26.)
13. **The parity contract.** Write the rule set that prevents this drift returning: what must always be shared, what may legitimately differ, and the CI check or review checklist that enforces it.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.

**Existing planning docs** — read the ones relevant to your track and write *on
top of* them rather than restating them: `docs/ROADMAP.md`, `docs/IMPROVEMENTS.md`,
`docs/CHECKLIST.md`, `docs/BIDDING_SYSTEM.md`, `docs/API.md`,
`docs/ARCHITECTURE.md`, `docs/STACK.md`, `docs/COST.md`, `docs/DEPLOYMENT.md`.
