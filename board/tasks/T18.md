## Mission

## Questions you must answer

1. Enumerate the fraud surface with a concrete scenario for each: (a) captain and accomplice running fake trips to farm incentives; (b) GPS spoofing to appear near demand or to simulate a completed trip; (c) rider creating accounts in bulk for first-ride promos; (d) promo-code sharing beyond intended limits; (e) referral self-dealing; (f) captain cancelling after arriving to collect a fee; (g) rider claiming a trip never happened to force a refund; (h) card testing against the payment endpoint; (i) wallet-credit laundering between colluding accounts; (j) captain account rental to unverified drivers. For each: is it currently possible, what would it cost the business, and what detects it.
2. Location trust: is a captain's reported position accepted verbatim? What plausibility checks exist — impossible speed between updates, teleportation, accuracy field, mock-location flag from the OS? Specify the server-side validator.
3. Rate limiting: the current KV-based limits (global 120/min, OTP 5/min, create-trip 10/min, location 30/min). Are they per-user, per-IP, or per-token? What defeats them (rotating tokens, shared IP behind CGNAT — the norm on Egyptian mobile networks)? Are the limits appropriate per endpoint?
4. Multi-accounting: what identifies a device? `routes/devices.ts` stores FCM tokens — is there any durable device fingerprint? Design one that works on Android and iOS without a heavyweight SDK.
5. Promo integrity: per-user caps, first-trip-only enforcement, code entropy, expiry, and whether validation is atomic with redemption (`POST /promos/validate` then apply — is there a window to redeem twice?).
6. Velocity rules: define the rule set that should run on trip completion and payout (trips per hour per captain, same rider-captain pair frequency, distance/fare ratio outliers, night-time anomalies) with concrete thresholds.
7. Risk scoring: design a lightweight scoring model that runs in a Worker — inputs, weights, thresholds, and the actions at each tier (allow, challenge, hold payout, review, ban).
8. Ops tooling: an analyst needs to see a flagged entity's history and act. Specify the queue and actions (coordinate with T11).
9. Payout holds: is there any hold period before a captain is paid, and can a payout be reversed after fraud is detected? (Coordinate with T04.)
10. Ban enforcement: when an account is banned, what actually stops the user — token revocation, device block, phone block? How long until the ban takes effect given KV eventual consistency?
11. Data needed: what must be logged now, before launch, so that fraud is investigable later? Retrofitting this data is impossible.
12. Cost of controls: each control has friction. Recommend the launch-minimum set versus the scale-up set.

## Benchmark against

- Uber: device fingerprinting, trip-anomaly ML, incentive-fraud teams, and driver-account-sharing detection via periodic selfie checks.
- inDrive: high-fraud emerging markets with cash — the closest analogue to Egypt's risk profile.
- Payments industry: velocity rules and hold periods as the standard primitives.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.

devices, geocode, intercity, payments, promo, safety, search, trips, user,
