## Questions you must answer

1. Build the cost model per 1,000 completed trips: Worker requests and CPU ms, D1 rows read and written, DO requests and duration-GB, KV reads/writes, R2 storage and operations, Queue messages, and egress. Then extrapolate to 1,000 / 10,000 / 50,000 trips per day, in USD per month. State every assumption.
2. Identify the top three cost drivers and what would halve each.
3. N+1 queries: audit the heaviest endpoints — admin trip lists, captain earnings, analytics, nearby captains. Quote the query patterns. How many D1 round-trips does one admin dashboard load cost?
4. D1 limits: maximum database size, statement duration, and the Worker subrequest cap. Which endpoint is closest to a limit, and what happens when the trips table reaches ten million rows?
5. Location write amplification: captains posting position every few seconds × hundreds of captains — how many writes per hour, to where (D1, DO storage, KV)? This is usually the number-one cost in ride-hailing on a serverless stack. Compute it and design the cheaper path.
6. DO duration billing: without hibernation, an idle WebSocket bills wall-clock time. Compute the monthly cost of 500 concurrent connections held for an hour, with and without hibernation (coordinate with T07).
7. Admin polling: `usePolling` intervals × pages × operators = requests per hour. Compute it and propose the event-driven alternative.
8. Cold starts and latency: measure or estimate p50/p95 for the three hottest endpoints. Where does Worker placement (Cairo traffic hitting which Cloudflare colo) affect latency, and does Smart Placement help or hurt given D1's location?
9. Flutter performance: cold start time, first-frame time, APK/IPA size, memory on a 2 GB device, and jank on the map screen. Name the specific costs (video splash decode, font files, image assets, package weight).
10. Payload sizes: are API responses trimmed, or do they return whole rows including fields the client ignores? Measure the trip-list and offer payloads. On Egyptian mobile data, bytes are money for the user too.
11. Caching opportunities: what is safely cacheable at the edge (vehicle types, pricing rules, geocode results, static config) and what would that save?
12. Scale-out plan: at what volume does D1 stop being viable, and what is the migration path — read replicas, Hyperdrive with Postgres, or sharding? Give the trigger metric, not just the option.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.
