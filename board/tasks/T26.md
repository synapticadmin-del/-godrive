## Questions you must answer

1. Build configuration: how does each app know which API to talk to? Is the base URL hardcoded, and is there a build-flavour mechanism for dev/staging/prod? If a tester's build points at production D1, say so loudly.
2. Signing: is release signing configured, and where do the keystore and credentials live? PR #19 claimed to add release signing — verify. Is a keystore committed to the repository (check `.gitignore`)? Is there a key-loss recovery plan (Play App Signing)?
3. Permissions audit: every permission requested in both manifests, with the justification. Background location for the captain app requires a specific Google Play declaration and a demo video — is the product ready for that review? This is a classic launch blocker; assess it seriously.
4. Obfuscation and hardening: is `--obfuscate --split-debug-info` used? Is there root/jailbreak detection, certificate pinning, or tamper detection for the captain app (which handles earnings)? What is proportionate here?
5. Versioning: how are `versionCode`/`versionName` managed, and do they correlate with the API's `APP_VERSION`? Is there a minimum-supported-version check so the server can force an upgrade when a breaking change ships? Design that mechanism — it is essential and appears absent.
6. Build automation: is there any CI that produces signed artefacts, or does someone build on a laptop (the `.bat` scripts suggest the latter)? Specify the pipeline for both platforms, including secret handling.
7. Crash reporting and analytics: absent as far as the inventory shows. Which SDK, what it costs in APK size, and what the privacy implications are (coordinate with T25).
8. App size: current APK/IPA estimate, and the contributors — `splash.mp4`, fonts, images, packages. Target size for the Egyptian market where storage and data are constrained.
9. Store listings: what is needed for both stores in Arabic and English — descriptions, screenshots, feature graphic, privacy policy URL, data-safety declarations, content rating, and the ride-hailing-specific policy requirements. Produce the checklist.
10. Review risk: enumerate the likely rejection reasons for both stores for a ride-hailing app (background location justification, account deletion requirement, payment policy, safety disclosures) and how to pre-empt each.
11. Update strategy: staged rollout percentages, kill switch for a bad release, and remote configuration so behaviour can change without a store submission.
12. iOS readiness in general: is the iOS side actually built and tested, or is this an Android-first project with an untouched iOS folder? Report the honest state.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.

**Existing planning docs** — read the ones relevant to your track and write *on
top of* them rather than restating them: `docs/ROADMAP.md`, `docs/IMPROVEMENTS.md`,
`docs/CHECKLIST.md`, `docs/BIDDING_SYSTEM.md`, `docs/API.md`,
