## Questions you must answer

1. Current state: read `ci.yml` and state exactly what runs on a pull request today. What is checked, what is not, and can a change that breaks the payment webhook merge without any signal?
2. Test strategy: design the pyramid for this stack — unit tests for pricing/fare/commission maths, integration tests for Worker routes against Miniflare or `wrangler dev` with a real D1 binding, DO tests, contract tests between the Flutter client and the API, and Flutter widget/golden tests. Name the tools that actually work with Workers and Flutter.
3. The critical-path test list: enumerate the twenty tests that must exist before launch, ranked. Start with the ones where a bug costs money — fare calculation, commission, wallet debit idempotency, webhook HMAC, accept-race serialisation, promo application.
4. Migration testing: `check_migrations_apply.py` exists. Does CI apply all 19 migrations to a fresh D1 and assert the resulting schema? Does it test applying them to a *populated* database?
5. Flutter CI: is anything built or analysed in CI for the two apps? `flutter analyze`, `flutter test`, and a build for both platforms should gate merges. Specify the workflow (but do not commit it — the app lacks the workflows permission; put the YAML in your document).
6. Environments: `wrangler.toml` declares dev, staging and prod. Is staging real — with its own D1, KV, R2 and secrets — and does anything deploy to it automatically? Is there a smoke test after deploy?
7. Deployment: PR #46 moved API deploys to CI from main. Verify the current mechanism, and assess whether there is any approval gate, changelog, or version tagging.
8. Rollback: what is the procedure when a bad deploy ships? Workers support version rollback — is it documented and practised? What about a bad migration, which is not reversible?
9. Feature flags: none appear to exist. Design a minimal flag mechanism (KV or `system_config`-backed) so risky changes can ship dark. This unblocks everything else in this plan.
10. Database seeding: can a developer get a realistic local environment with one command? What is missing?
11. Load testing: has this ever been load tested? Design the test — concurrent trip creation, dispatch fan-out, WebSocket connection storm — with target numbers and the tool to use.
12. Code quality gates: linting, formatting, type strictness (`tsconfig` settings), dependency audit, secret scanning. What is enforced, what should be.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.

**Existing planning docs** — read the ones relevant to your track and write *on
top of* them rather than restating them: `docs/ROADMAP.md`, `docs/IMPROVEMENTS.md`,
`docs/CHECKLIST.md`, `docs/BIDDING_SYSTEM.md`, `docs/API.md`,
`docs/ARCHITECTURE.md`, `docs/STACK.md`, `docs/COST.md`, `docs/DEPLOYMENT.md`.

**Known history.** ~58 PRs have landed. Several claim fixes relevant to these
tracks (security hardening in #19–#22, dispatch work in #8/#14, realtime fixes
in #47/#53, admin repairs in #40/#42, design-system migrations in #12/#15/#18/#35/#36).
Treat every such claim as unverified until you read the code on current `main`.

behaviour are marked as confident or assumed. Anything you could not verify is
