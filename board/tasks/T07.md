## Questions you must answer

1. WebSocket authentication: PR #22/#23 moved to a first-message auth scheme. Is the socket usable before that message arrives? Is there a timeout that closes unauthenticated sockets? Can a client subscribe to a `TripRoom` it is not a participant in?
2. DO addressing: how is a `TripRoom` id derived from a trip? PR #47 fixed riders missing updates because `TripRoom` was looked up by the wrong id — verify the fix is complete and that both sides derive the same id.
3. Hibernation: does the code use the WebSocket Hibernation API? Without it, every idle connection holds a DO in memory and bills for wall-clock duration. Quantify the difference at 1,000 concurrent trips.
4. Message contract: is there a versioned envelope, or ad-hoc JSON? What happens when an old app build receives a new message type?
5. Ordering and loss: are messages sequenced? If a client misses a `trip.status` transition while reconnecting, does it resync from REST, or sit in a stale state forever?
6. Reconnection: backoff strategy, jitter, max attempts, and behaviour on network flap or app backgrounding on Android. What does the rider see during a reconnect — stale car position or an honest indicator?
7. Fallback: PR #53 added polling as a backstop. Is polling always running (double cost) or only on WS failure? What is the poll interval and does it stop on foreground/background transitions?
8. State ownership: does the DO hold authoritative trip state, or is D1 the source of truth with the DO as a fan-out bus? Mixed ownership is the usual source of split-brain — determine which it is and whether it is consistent.
9. `OfferScheduler` alarms: what schedules them, are they cancelled when a trip is accepted or cancelled, and can an orphaned alarm keep firing and billing forever?
10. Location fan-out volume: at what frequency does a captain's position reach a rider, how many messages per trip, and what is the bandwidth cost on a metered Egyptian mobile plan?
11. Backpressure: what happens when a client is slow — unbounded buffering in the DO?
12. Failure blast radius: if `CaptainInbox` for one captain throws, does it take down anything else? Is there error isolation and alerting?

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.
