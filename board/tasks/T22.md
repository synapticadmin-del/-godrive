## Questions you must answer

1. Logging: what is logged today, in what format, and where does it go? Is it structured JSON with a request id, or `console.log` strings? Can you correlate a rider's complaint to the request that failed?
2. Request tracing: is there a correlation id flowing from the Flutter client through the Worker into the DOs and back? Without it, debugging a distributed trip is guesswork. Specify the propagation scheme.
3. Metrics: what business and technical metrics exist? Design the set that matters — trips created/accepted/completed/cancelled, time-to-match, dispatch fill rate, payment success rate, WS connection count and drop rate, p50/p95/p99 latency per route, error rate by code, D1 query duration, DO invocation count.
4. Alerting: what would page someone? Define the alert set with thresholds and severity — payment webhook failures, DLQ depth, dispatch fill rate collapse, auth error spike, D1 errors, cron failure. Today, presumably, nothing alerts. Say so plainly.
5. Client-side error reporting: is there any crash reporting in the Flutter apps (Crashlytics/Sentry) or the admin? Without it, mobile bugs are invisible. Specify the integration and the privacy considerations.
6. Cloudflare-native tooling: Workers Analytics Engine, Tail Workers, Logpush — which are configured, which should be, and what they cost. Give concrete `wrangler.toml` additions.
7. Health checks: is there a `/health` endpoint that actually verifies D1, KV, R2 and DO reachability? What monitors it externally?
8. The audit log as an operational tool: is `audit_log` queryable at speed, complete, and immutable? (Coordinate with T02 and T08.)
9. Cron observability: two crons run (scheduled dispatch every minute, monthly invoices). How would anyone know if one stopped? Cloudflare cron failures are silent by default.
10. Queue health: the NOTIFICATIONS queue has a DLQ. Who drains it? What happens to a customer whose notification is in there?
11. Runbooks: write the operational runbooks for the five most likely incidents — payments down, dispatch not matching, WebSocket mass disconnect, D1 degraded, a bad deploy. Each with detection, diagnosis steps, mitigation, and rollback.
12. On-call and SLOs: define realistic SLOs for a launch-stage product (availability, time-to-match, payment success) and the error budget policy.

## Shared context (identical for every task)

**Synaptic Go** is an Egyptian ride-hailing platform, currently pre-production.
The product goal is a transport and delivery app with the feature depth of Uber
and the price-negotiation model of inDrive, hardened to full production quality.

**Stack.** Cloudflare Workers (Hono-style routing) + D1 (SQLite) + KV
(`SESSIONS`) + R2 (`FILES`) + four Durable Objects (`TripRoom`, `GeoCell`,
`CaptainInbox`, `OfferScheduler`) + Queues (`NOTIFICATIONS` with a DLQ) + two
cron triggers (scheduled-trip dispatch every minute, B2B invoices monthly).
Two Flutter apps (`apps/rider`, `apps/captain`) sharing `packages/flutter_shared`.
A React + Vite admin console (`apps/admin`). 19 D1 migrations. `APP_VERSION 0.4.0`.

**API surface.** `apps/api/src/routes/`: admin, auth, captain, companies,
devices, geocode, intercity, payments, promo, safety, search, trips, user,
wallet. `apps/api/src/lib/`: audit, cleanup, geocode, jwt, nearby, notifications,
paymob, pricing, routing, schemas, turnstile, types, utils.
`apps/api/src/middleware/`: auth, rateLimit.
