## What I actually did

1. **`scripts/backup-d1.sh`** — `wrangler d1 export --remote` (database name parsed out of
   `wrangler.toml`, never hardcoded, same idiom as `deploy.sh`), check the dump before storing it,
   write a `.manifest.json` sidecar carrying sha256 + the remote `d1_migrations` list, upload dump
   and manifest to a **dedicated** `synaptic-go-backups` bucket, then **download the object again
   and compare sha256**, failing if they differ. An upload nobody read back is root R3 in miniature.
2. **`docs/RUNBOOK-restore.md`** — triage across three procedures, the restore step by step,
   verification queries that name the effect, cutover as a separate decision, honest RPO/RTO, and a
   rehearsal-record table with one row filled and one deliberately empty.
3. **The rehearsal found a real defect.** A `.dump`-shaped export lists tables **alphabetically**,
   so `audit_log`/`captains`/`payout_requests` load before `users` and the replay dies with
   `no such table: main.users`. **`PRAGMA defer_foreign_keys` — Cloudflare's documented remedy —
   does not fix it** (deferral postpones constraint checking; this is name resolution), and
   `PRAGMA foreign_keys = OFF` does not exist on D1. The runbook therefore prescribes
   schema-from-`migrations/` + data-from-dump, and the drill asserts all four strategies every run.
4. **Tests, all offline:** `--self-test` 26 assertions, `--rehearse` 21 assertions (20 migrations →
   37 tables, restored copy byte-identical across all 37, 0.136 s), `--check-dump` 7 assertions.
   Mutation-tested against 8 deliberate breakages; all 8 turn the self-test red. Two real faults were
   caught that way and fixed: an over-broad `d1 execute` guard, and — **nothing in this repo carries
   the executable bit**, `deploy.sh` included — every `./scripts/backup-d1.sh` would have failed with
   "Permission denied" on a fresh clone. All invocations are now `bash scripts/backup-d1.sh`.
5. **`docs/plan/assets/e18-backup-d1-schedule.yml`** — nightly workflow for a human to install.
