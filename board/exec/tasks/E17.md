> **Goal.** Make an Android release physically possible and not dangerous.

## Why this blocks launch

`targetSdk = 34` is below Play's floor of 35, so upload is rejected outright — submission is impossible today, verified on main. The release build's signing config is a ternary that falls back to `signingConfigs.debug` when `key.properties` is absent, also verified: it produces a build that looks shippable, cannot be uploaded, and if it ever reached users could never be upgraded to a real-key build without them uninstalling (T26 F-26-02, called 'the most dangerous line in the mobile codebase'). Builds currently come from one Windows laptop with paths hardcoded to `C:\Users\kayf\…`.

## Scope

- `targetSdk` 35 on both apps; check the behaviour changes that come with it.
- Invert the signing conditional to **fail closed**: a release build with no keystore throws `GradleException`. Enrol in Play App Signing.
- Strip `UIBackgroundModes` and the always-location usage string from the **rider** `Info.plist` — declared, unimplemented, and a review risk (F-26-05). Leave the captain's alone; E11 is implementing it there.
- Produce the signed artefact in CI. The workflow YAML cannot be committed by an agent — put it at
  `docs/plan/assets/` and name the human step in the PR. The human who does E00 installs it; flag it there so
  the two workflow installs happen in one sitting.

## Acceptance criteria

- A release build with no keystore fails the build instead of producing a debug-signed APK.
- Both apps target API 35.
- A signed artefact exists that nobody's laptop produced.

## Out of scope

edit it. Another chat owns it and your change will be silently lost or will lose theirs.

## Definition of done

1. One PR into `main`, small enough to read in one sitting.
2. If this brief names tests, they exist and run in CI. **If it names none, say so in the PR and
   stop there** — do not invent a test harness. `ci.yml` runs `flutter analyze` and never
   `flutter test`, so a Dart test you add today runs nowhere; wiring that up needs a workflow edit
   no agent can make. Propose it in the PR body and leave it to a human (see WAVE-PLAN §9).
3. You do **not** merge it yourself.
4. After merge, a different chat verifies the *effect* against `main` and closes the finding. You move it
   to `awaiting-verification` and stop.
