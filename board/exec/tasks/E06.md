> **Goal.** Stop creating an unbounded, silent liability to captains.

## Why this blocks launch

`wallet.ts:113-130` debits the captain's balance into a `status='pending'` row that no endpoint and no screen can ever action (T04 F-04-06, T03 F-03-08, T11 F-11-04 — three tracks, same defect). There is no disbursement API and no bank-account storage. T04's author asks for this to ship before anything else in that track, because it is actively accruing liability for every captain who taps withdraw.

## Scope

- Keep the endpoint. Stop debiting on request.
- Record the request in a new `payout_requests` table in a `requested` state (take the next migration number via the migration lock).
- Debit only when an operator marks it paid — the operator surface itself is E14's.
- Add the `idempotency_key` the insert has always lacked, despite migration 0005 adding the column.

## Acceptance criteria

- Requesting a payout does not change `users.wallet_balance`.
- Every existing stranded `pending` row is enumerable by a query included in the PR description, so finance can reconcile them by hand.
- A repeated identical request creates one row, not two.
