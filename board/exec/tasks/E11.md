> **Goal.** Make the captain visible — the product's core promise.

## Why this blocks launch

One pipeline, four independent breaks, found by four tracks that never spoke (root R5). Location publishes only on 50 m of movement with no time floor, so a **stationary** captain ages out of the GeoCell after 120 s and stops being dispatchable (F-06-02). Backgrounding the app cancels the GPS stream while D1 still says `is_online = 1` (F-06-03, F-10-01) — which happens every time the captain opens Google Maps. And at driving speed the publish rate is 1.7–3.9× the server's own rate limit, so the excess is 429'd and discarded: the rider watches the car move, freeze for 38–47 s, then teleport (F-07-01). The trap: lengthening the interval to respect the limit makes the marker look **worse** unless interpolation ships in the same release — T13 and T28 both say so explicitly.

## Scope

- Add an unconditional periodic heartbeat independent of movement.
- Add an Android foreground service with `foregroundServiceType="location"` so GPS survives backgrounding; call `POST /captain/online {online:false}` when it genuinely stops.
- Reconcile client cadence with the server limit — and move the rate-limit counter into the `GeoCell` DO the request already contacts (T24 P0.3) rather than paying KV per write.
- Ship `AnimatedVehicleMarker` with `LatLngTween` in `flutter_shared` **in the same release**. Linear interpolation, tween over the measured inter-fix interval, never extrapolate.
- Fix the hibernation bug while you are in `TripRoom`/`CaptainInbox`: per-connection state must use `ws.serializeAttachment()`, not an in-memory `Map` (F-07-02).

## Acceptance criteria

- A stationary online captain still receives offers after five minutes.
- Backgrounding the app does not stop location, and the rider's marker keeps moving.
- No location POST is 429'd during a normal drive.
- The marker moves smoothly between fixes rather than jumping.
- **Do not ship the cadence change without the interpolation.**
