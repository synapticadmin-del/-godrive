> **Goal.** Be able to get the money back.

## Why this blocks launch

The only backup is platform-default D1 Time Travel: never rehearsed, and restoring it is a *destructive in-place overwrite* (T08 F-08-04). For a system holding wallet balances, 'we think we can restore' is not a position from which to launch. The author calls this a go-live blocker in those words.

## Scope

- A scheduled export of D1 to R2, retained on a stated schedule.
- A restore runbook in `docs/RUNBOOK-restore.md`.
- **Execute the restore at least once** against a scratch database and record the wall-clock time and the exact commands in the runbook. A runbook nobody has run is root R3 again — an artefact created whose effect was never verified.

## Acceptance criteria

- An export lands in R2 on schedule and its size is monitored.
- The runbook has a completed-rehearsal line with a date, a duration and a named person.
- Restoring does not require improvisation at 3 a.m.

## Out of scope

Anything touching a file not in `owns`. If you believe you need one, stop and say so on the PR — do not
edit it. Another chat owns it and your change will be silently lost or will lose theirs.

## Definition of done

1. One PR into `main`, small enough to read in one sitting.
2. The tests named above exist and run in CI.
3. You do **not** merge it yourself.
4. After merge, a different chat verifies the *effect* against `main` and closes the finding. You move it
   to `awaiting-verification` and stop.
