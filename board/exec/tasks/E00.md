> **Goal.** Make every other gate item enforceable, and let the API deploy from `main`.

## Why no agent can do this

Two hard blocks, both verified:

1. **Branch protection is a repository setting, not a file.** The GitHub App this programme runs on
   cannot change it. Verified via the branch API on `main` at `b0c0866`: `protected: false`,
   `required_status_checks.enforcement_level: "off"`, `contexts: []`.
2. **`.github/workflows/**` is not writable by the App** — it has no `workflows` permission. Every
   push to that path fails. This is exactly how the repository ended up here: PR #46, titled
   *"ci: deploy the API from main instead of from someone's laptop"*, merged with the workflow
   committed to `docs/ci/deploy-api.yml` instead. It has never run.

## What to do — about five minutes

1. **Settings → Branches → add a rule for `main`:** require a pull request before merging, require
   status checks to pass, and select the existing `ci.yml` checks as required. Optionally require one
   approving review — PROTOCOL-EXEC §7 forbids self-merge regardless.
2. **Install the deploy workflow** from a clone with push rights:

```bash
git mv docs/ci/deploy-api.yml .github/workflows/deploy.yml
git commit -m "ci: install the deploy workflow that PR #46 was supposed to install"
git push
```

   The file is already well built — it typechecks, tests, applies migrations with
   `wrangler d1 migrations apply --remote --env prod`, deploys with `--env prod`, then smoke-tests.
   It has simply never been in a location where GitHub would run it. E01 fixes the three defects in
   it and in `deploy.sh`.
3. **Confirm production migration state** before anything else ships. `docs/DEPLOYMENT.md:74-79`
   claims 17 applied and "nothing pending"; the repository has 19:

```bash
wrangler d1 migrations list synaptic-go --remote --env prod
```

## Acceptance criteria

- A PR with a failing check cannot be merged into `main`.
- A push to `main` triggers a deploy run, and the run URL is recorded in `PROJECT.md`.
- The output of the migrations-list command is pasted into **your `PROJECT.md` block and the commit
  message** — *not* into `docs/DEPLOYMENT.md`. E01 owns that file and records the verified state there;
  two writers on one file is the exact collision this board exists to prevent.
