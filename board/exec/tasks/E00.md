> **Goal.** Make every other gate item enforceable, and let the API deploy from `main`.

## Why no agent can do this

Two hard blocks, both verified:

1. **Branch protection is a repository setting, not a file.** The GitHub App this programme runs on
   cannot change it. Verified via the branch API on `main` at `b0c0866`: `protected: false`,
   `required_status_checks.enforcement_level: "off"`, `contexts: []`.
2. **`.github/workflows/**` is not writable by the App** — it has no `workflows` permission. Every
   push to that path fails. This is exactly how the repository ended up here: PR #46, titled
   *"ci: deploy the API from main instead of from someone's laptop"*, merged with the workflow
   committed to `docs/ci/deploy-api.yml` instead. It has never run.

## What to do — about five minutes

1. **Protect `main` — but use a ruleset, not classic branch protection, and do it LAST.**

   The three required contexts are the `name:` values of `ci.yml`'s jobs, exactly:
   `node (typecheck, build, tests)` · `flutter (analyze)` · `checks (migrations, l10n, hygiene)`.
   A character wrong here creates a check that never arrives and the branch blocks forever.

   > **This conflicts with PROTOCOL-EXEC §5.5 and you must resolve it deliberately.** Every chat pushes
   > its `PROJECT.md` block **directly to `main`** — that is the one write to `main` a chat may make, and
   > five chats have already done it. GitHub rejects a direct push to a branch carrying required status
   > checks (`GH006 … Required status check is expected`), because the pushed commit has no checks yet.
   > Naive protection therefore breaks the board's bookkeeping for every future task. A **ruleset** can
   > carry a `bypass_actors` entry for the identity the chats push as; classic protection cannot exempt
   > anyone from status checks. Enable it, then confirm the next chat's `PROJECT.md` append still lands —
   > that is the test, and it is the one that will bite you.

   Leave `strict_required_status_checks_policy` **false**. "Require branches to be up to date" makes
   every merge invalidate every other open PR and forces a rebase plus a full CI re-run — it serialises
   a board designed to run five chats wide, for no safety gain when the PRs touch disjoint files.

   Do this **after** steps 2–4, not before: each of those is itself a direct push or a merge.
2. **Install the deploy workflow** from a clone with push rights:

```bash
git mv docs/ci/deploy-api.yml .github/workflows/deploy.yml
git commit -m "ci: install the deploy workflow that PR #46 was supposed to install"
git push
```

   The file is already well built — it typechecks, tests, applies migrations with
   `wrangler d1 migrations apply --remote --env prod`, deploys with `--env prod`, then smoke-tests.
   It has simply never been in a location where GitHub would run it.

   **Correction, 2026-08-01:** this brief previously said "E01 fixes the three defects in it and in
   `deploy.sh`". E01 (PR #89) touches `apps/api/deploy.sh`, `apps/api/package.json`,
   `docs/DEPLOYMENT.md` and `package-lock.json` — **not** `docs/ci/deploy-api.yml`. The workflow ships
   as-is. Review it at install time, because the moment it lands under `.github/workflows/` no chat can
   ever edit it again. It was read at `main` and is correct on the points that matter: `--env prod` on
   both the migration and the deploy, `working-directory: apps/api` (which is what makes
   `migrations_dir = "../../migrations"` resolve), and a real smoke test against the `[[routes]]` host.

   **One behaviour to be deliberate about:** with no `CLOUDFLARE_API_TOKEN` secret, the workflow reports
   *"Deploy skipped"* and exits **green**. That is intentional, and it is also the artefact/effect trap
   in §7 of PROTOCOL-EXEC. A green skipped run is not evidence the deploy works, and closing gate item 2
   on one is root R3 — the exact thing PR #46 already did to this repository once. Prove the pipeline
   with a `workflow_dispatch` run whose log does **not** contain "Deploy skipped", and record the live
   `GET /health` → `200` separately from the workflow's own summary.
3. **Confirm production migration state** before anything else ships. `docs/DEPLOYMENT.md:74-79`

## Acceptance criteria

- A PR with a failing check cannot be merged into `main`.
- A push to `main` triggers a deploy run, and the run URL is recorded in `PROJECT.md`.
- The output of the migrations-list command is pasted into **your `PROJECT.md` block and the commit
  message** — *not* into `docs/DEPLOYMENT.md`. E01 owns that file and records the verified state there;
  two writers on one file is the exact collision this board exists to prevent.

## 4. Ongoing — the round boundary is yours too

**Added 2026-08-01, after round 1 stalled on this exact gap.**

`PROTOCOL-EXEC` §8 forbids every chat from merging any PR, including its own. §7 has the author stop at
`awaiting-verification` and a *different chat* verify **after the merge**. Nothing in the board said who
performs that merge. The result: round 1 finished with five tasks `done`, five PRs green on all three
checks, and **zero** of their code on `main` — and every task in rounds 2–6 correctly refused to start,
because `depends_on` requires a *merged* dependency, not a finished one.

So it is a standing duty, and it is yours:

**At each round boundary,** for every PR whose claim is `status: done`:

1. Confirm all three checks are green (`gh pr checks <n>`).
2. Merge it — `--squash` or `--merge`, never `--rebase` (rebasing rewrites the chat's commit and breaks
   the sha its claim records).
3. Watch the CI run on `main` afterwards. When two migrations merge in the same round, that run is the
   first time they apply **together** to a fresh database; each PR only ever tested its own.
4. Say on the PR that it is merged, so a verifier can pick it up. You do **not** verify it yourself and
   you do **not** close its findings — that is a different chat's job, and it must not read the author's
   summary before forming a view.

Round 1's five PRs are **#89** (E01), **#88** (E05), **#90** (E06), **#91** (E11) and **#92** (E16). They
touch disjoint file sets, so order does not matter for conflicts; **#89** first is still the right call,
because all of round 2 (`E02`, `E17`, `E18`) depends on `E01`.
