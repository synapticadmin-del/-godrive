## 1. السيناريو الأساسي: رحلة ناجحة من الطلب للإتمام

### التدفق الكامل

```
العميل                          النظام                          الكابتن
  |                               |                               |
  |--[1] طلب تقدير أجرة---------->|                               |
  |                               |--[2] OSRM route + fare calc   |
  |<--[3] تقدير + كباتن قريبين----|                               |
  |                               |                               |
  |--[4] تأكيد الطلب------------->|                               |
  |                               |--[5] إنشاء رحلة (searching)   |
  |                               |--[6] بحث GeoCell (9 خلايا)    |
  |                               |--[7] فلترة بنطاق الكابتن     |
  |                               |--[8] staged rollout (3/15s)  |--[9] FCM + Inbox push
  |                               |                               |
  |                               |<--[10] قبول الرحلة------------|
  |                               |--[11] تعيين + broadcast       |
  |<--[12] إشعار "تم القبول"------|                               |
  |                               |                               |
  |                               |<--[13] updates الموقع كل 30s--|
  |<--[14] تحديثات لحظية----------|                               |
  |                               |                               |
  |                               |<--[15] "وصلت" (arrived)-------|
  |<--[16] إشعار "وصل الكابتن"----|                               |
  |                               |                               |
  |                               |<--[17] "بدأت الرحلة"----------|
  |<--[18] إشعار "بدأت"-----------|                               |
  |                               |                               |
  |                               |<--[19] "انتهت الرحلة"---------|
  |                               |--[20] حساب الأجرة النهائية    |
  |                               |--[21] تحديث المحافظ           |
  |<--[22] إشعار "وصلت بسلامة"----|                               |
  |                               |                               |
  |--[23] تقييم الكابتن---------->|                               |
  |                               |--[24] تحديث متوسط التقييم     |
```

### الخطوات التفصيلية

| # | الخطوة | الجهة | Endpoint/الآلية | ملاحظات |
|---|--------|-------|-----------------|---------|
| 1 | طلب تقدير | العميل | `POST /trips/estimate` | بدون auth — rate limit 30/دقيقة |
| 2 | حساب المسار | النظام | OSRM `getRoute()` | fallback للـ haversine عند فشل OSRM |
| 3 | عرض التقدير | العميل | response | يشمل الكباتن القريبين (15 كم) |
| 4 | تأكيد الطلب | العميل | `POST /trips` | auth rider + rate limit 10/دقيقة |
| 5 | إنشاء الرحلة | النظام | `INSERT INTO trips` | status = searching |
| 6 | البحث عن كباتن | النظام | `findNearbyCaptains()` | 9 geohash cells (~7 كم) |
| 7 | فلترة النطاق | النظام | `filterByCaptainRadius()` | يحترم search_radius_km لكل كابتن |
| 8 | Staged rollout | النظام | `OfferScheduler` DO | 3 كباتن كل 15 ثانية |
| 9 | إشعار الكابتن | النظام | FCM + CaptainInbox | "رحلة جديدة متاحة" |
| 10 | قبول الرحلة | الكابتن | `POST /trips/:id/accept` | online guard + busy guard |
| 11 | التعيين | النظام | conditional UPDATE | status = assigned |
| 12 | إشعار العميل | النظام | FCM | "تم قبول رحلتك" |
| 13 | تحديث الموقع | الكابتن | `POST /captain/location` | كل 30 ثانية تلقائيًا |
| 14 | بث الموقع | النظام | TripRoom WebSocket | العميل يرى الكابتن يتحرك |
| 15 | وصول الكابتن | الكابتن | `POST /trips/:id/arrived` | status = arrived |
| 16 | إشعار الوصول | النظام | FCM | "الكابتن وصل" |
| 17 | بدء الرحلة | الكابتن | `POST /trips/:id/start` | status = in_progress |
| 18 | إشعار البدء | النظام | FCM | "بدأت الرحلة" |
| 19 | إتمام الرحلة | الكابتن | `POST /trips/:id/complete` | status = completed |
| 20 | حساب الأجرة | النظام | accepted_price ?? estimated | حسب طريقة الدفع |
| 21 | تحديث المحافظ | النظام | wallet_transactions | كاش: خصم عمولة من الكابتن؛ محفظة: خصم من العميل + إضافة للكابتن |
| 22 | إشعار الإتمام | النظام | FCM للطرفين | "وصلت بسلامة" / "اكتملت الرحلة" |
| 23 | التقييم | العميل | `POST /trips/:id/rate` | 1-5 + تعليق اختياري |
| 24 | تحديث المتوسط | النظام | `UPDATE captains` | AVG + COUNT |

## 2. سيناريو المزايدة والتفاوض

### التدفق

```
العميل                          النظام                          الكابتن
  |                               |                               |
  |--[1] طلب رحلة بسعر مقترح----->|                               |
  |                               |--[2] searching + rollout      |
  |                               |                               |--[3] يرى العرض
  |                               |<--[4] عرض سعر مضاد (bid)------|
  |                               |--[5] status = offered         |
  |<--[6] إشعار "عرض جديد"--------|                               |
  |                               |                               |
  |--[7] يفتح قائمة العروض------->|                               |
  |<--[8] قائمة بالكباتن + ETA----|                               |
  |                               |                               |
  |--[9] يقبل عرض كابتن معين----->|                               |
  |                               |--[10] تعيين + إلغاء باقي العروض|
  |                               |--[11] إشعار الكابتن الفائز    |--[12] "تم قبول عرضك"
  |<--[13] تحديث الحالة-----------|                               |
```

### النقاط الحرجة

| النقطة | الوصف | المصدر |
|--------|-------|--------|
| ETA حقيقي | OSRM table service — ليس خط مستقيم | `attachCaptainEtas` |
| KV cache | 60 ثانية لكل كابتن/رحلة — يمنع OSRM flood | `trips.ts` |
| Atomic acceptance | `UPDATE ... WHERE status IN ('searching','offered')` | `trips.ts` |
| Rollback العروض | الفائز accepted، الباقي rejected تلقائيًا | `trips.ts` |
| إشعار الفائز | FCM + Inbox — يوقظه حتى لو مغلق التطبيق | `trips.ts` |

## 3. سيناريوهات الإلغاء

### 3.1 إلغاء العميل قبل القبول

| الخطوة | الحدث | التأثير |
|--------|-------|---------|
| 1 | العميل يلغي searching/offered | status = cancelled |
| 2 | OfferScheduler teardown | لا مزيد من الدفعات |
| 3 | Cancel fanout | 25 كابتن في النطاق يُشعَرون |
| 4 | Inbox push | "trip.cancelled" لكل كابتن رأى العرض |

**الضمانات:** لا يمكن لكابتن قبول رحلة ملغاة — `canTransition` يمنعها.

### 3.2 إلغاء العميل بعد القبول

| الخطوة | الحدث | التأثير |
|--------|-------|---------|
| 1 | العميل يلغي assigned/arrived | status = cancelled |
| 2 | إشعار الكابتن | "ألغى الراكب الرحلة" |
| 3 | الكابتن يتحرر | يمكنه قبول رحلة جديدة |

**ملاحظة:** لا توجد غرامة إلغاء للعميل في الكود الحالي — `cancel_fee_egp` موجود في system_config لكن لا يُطبق.

### 3.3 إلغاء الكابتن بعد القبول

| الخطوة | الحدث | التأثير |
|--------|-------|---------|
| 1 | الكابتن يلغي assigned/arrived/in_progress | status = cancelled |
| 2 | إشعار العميل | "تم إلغاء رحلتك — يمكنك طلب جديدة" |
| 3 | العميل يعيد الطلب | رحلة جديدة بحث جديد |

**الضمانات:** `canTransition` يسمح بالإلغاء من أي حالة قبل completed.

### 3.4 إلغاء الأدمن

| الخطوة | الحدث | التأثير |
|--------|-------|---------|
| 1 | الأدمن يلغي من اللوحة | نفس تدفق 3.2/3.3 |
| 2 | Audit log | `logAudit` بالسبب |

## 4. سيناريوهات الدفع

### 4.1 دفع كاش

```
الرحلة تنتهي → الكابتن يحصّل الأجرة يدويًا → النظام يخصم العمولة من محفظة الكابتن
```

| الخطوة | الحساب | المصدر |
|--------|--------|--------|
| 1 | final_fare = accepted_price ?? estimated | `trips.ts` |
| 2 | commission = fare × commission_rate | `trips.ts` |
| 3 | خصم العمولة من محفظة الكابتن | `wallet_transactions` type=commission, direction=debit |
| 4 | الكابتن يحتفظ بالباقي نقدًا | خارج النظام |

**الضمانة:** idempotency_key = `trip_commission_debit:{tripId}` — لا خصم مزدوج.

### 4.2 دفع بالمحفظة

```
الرحلة تنتهي → النظام يخصم من محفظة العميل → يضيف صافي الأجرة لمحفظة الكابتن
```

| الخطوة | الحساب | الضمانة |
|--------|--------|--------|
| 1 | خصم الأجرة من العميل | conditional UPDATE `wallet_balance >= fare` |
| 2 | إذا فشل الخصم | status = failed — لا إتمام |
| 3 | إضافة (fare - commission) للكابتن | idempotency_key = `trip_payout:{tripId}` |

### 4.3 دفع بالبطاقة (Paymob)

```
العميل يدفع مسبقًا → webhook يؤكد → الرحلة تُعلَّم "paid"
```

| الخطوة | الحدث | الضمانة |
|--------|-------|--------|
| 1 | إنشاء intention | `payment_intentions` سجل |
| 2 | webhook من Paymob | HMAC-SHA512 verification |
| 3 | تحقق المبلغ | amount_cents == intention.amount_piastres |
| 4 | تحديث الرحلة | `payment_status = 'paid'` |
| 5 | idempotency | intention-level — لا double-credit |

### 4.4 شحن المحفظة

| الخطوة | الحدث | الضمانة |
|--------|-------|--------|
| 1 | العميل يطلب شحن | `POST /payments/paymob/intention` purpose=wallet_topup |
| 2 | webhook نجاح | HMAC + amount check |
| 3 | إضافة للمحفظة | `wallet_transactions` type=topup, direction=credit |
| 4 | إشعار | "تم شحن المحفظة" |

## 6. الحالات الحدّية (Edge Cases)

### 6.1 سباق القبول (Race Condition)

**السيناريو:** كابتنان يضغطان "قبول" في نفس اللحظة.

**الحل:** conditional UPDATE
```sql
UPDATE trips SET status = 'assigned', captain_id = ?
WHERE id = ? AND status IN ('searching','offered')
```
الفائز: `meta.changes = 1`. الخاسر: 409 `TRIP_TAKEN`.

### 6.2 كابتن يقبل رحلة وهو مشغول

**السيناريو:** كابتن له رحلة نشطة يحاول قبول أخرى.

**الحل:** busy guard
```typescript
if (captain has trip in ['assigned','arrived','in_progress']) return 409 BUSY
```

### 6.3 كابتن offline يحاول قبول رحلة

**السيناريو:** كابتن أغلق التطبيق لكن الـ UI لم يحدّث.

**الحل:** online guard
```typescript
if (!captain.is_online && role !== 'admin') return 403 OFFLINE
```

### 6.4 رصيد محفظة غير كافٍ

**السيناريو:** العميل اختار محفظة لكن الرصيد أقل من الأجرة.

**الحل:** conditional debit
```sql
UPDATE users SET wallet_balance = wallet_balance - ?
WHERE id = ? AND wallet_balance >= ?
```
إذا `changes = 0` → 400 `INSUFFICIENT_BALANCE`.

### 6.5 انقطاع الاتصال أثناء الرحلة

**السيناريو:** العميل/الكابتن فقد الاتصال.

**السلوك:**
- الموقع يتوقف عن التحديث (آخر نقطة تبقى)
- الـ WebSocket يُغلق — العميل يعيد الاتصال تلقائيًا
- الرحلة تستمر في النظام — لا إلغاء تلقائي

### 6.6 Paymob webhook متكرر

**السيناريو:** Paymob أعاد إرسال webhook.

**الحل:** idempotency_key = `paymob:{orderId}:{txnId}` — `INSERT OR IGNORE`.

### 6.7 OSRM غير متاح

**السيناريو:** خدمة الخرائط توقفت.

**الحل:** fallback لـ haversine — ETA يُعلَّم `eta_source: 'haversine'`.

### 6.8 كابتن لم يحدّث موقعه منذ 10 دقائق

**السيناريو:** ETA غير دقيق لأن الموقع قديم.

**الحل:** `ETA_MAX_LOCATION_AGE_MS = 10 * 60 * 1000` — لا ETA يُحسب.

### 6.9 عميل يلغي رحلة لها عروض معلقة

**السيناريو:** كابتن كتب عرضًا والعميل ألغى قبل القراءة.

**الحل:** cancel fanout — 25 كابتن يُشعَرون + العرض يُلغى من الـ Inbox.

### 6.10 رحلة مجدولة لم تجد كابتن

**السيناريو:** الوقت حان ولا يوجد كابتن متاح.

**السلوك:** الرحلة تبقى `searching` — الكورن يعيد المحاولة كل دقيقة. لا timeout تلقائي.

## 7. سيناريوهات Intercity

### 7.1 حجز ناجح

| الخطوة | الحدث | الضمانة |
|--------|-------|--------|
| 1 | العميل يتصفح routes | public — بدون auth |
| 2 | يختار schedule | يرى المقاعد المتاحة |
| 3 | يحجز مقاعد | conditional UPDATE `seats_booked + ? <= seats_total` |
| 4 | يدفع محفظة | خصم فوري مع rollback عند الفشل |
| 5 | يستلم QR | `qr_token` فريد |
| 6 | الكابتن يُشعَر | FCM "حجز مقعد جديد" |

### 7.2 إلغاء حجز

| الخطوة | الحدث | الضمانة |
|--------|-------|--------|
| 1 | العميل يلغي قبل المغادرة | `POST /intercity/bookings/:id/cancel` |
| 2 | تحقق من الحالة | لا إلغاء بعد المغادرة أو الصعود |
| 3 | إطلاق المقاعد | `seats_booked - ?` |
| 4 | استرداد للمحفظة | إذا دفع محفظة — إضافة refund |
| 5 | إشعار الكابتن | "إلغاء حجز" |

### 7.3 صعود الراكب

| الخطوة | الحدث | الضمانة |
|--------|-------|--------|
| 1 | الكابتن يمسح QR | `POST /intercity/captain/board/:bookingId` |
| 2 | تحقق | `qrToken == booking.qr_token` |
| 3 | تسجيل | `status = 'boarded'` |
| 4 | لا إلغاء | الراكب لا يمكنه الإلغاء بعد الصعود |
